# ひまつぶし工房：作業者への共通の指示

このリポジトリで作業するときは、最初にこの文書を読み、ここに書いたことを守ってください。作業の指示とこの文書が食い違うときは、指示を出した人に確かめてください。

## 0. まず読むもの
1. `HANDOFF.md`（公開のしかた、決まりごと）
2. `docs/AUDIT.md`（今の状態と、わかっている不具合）
3. `docs/SYSTEM_ARCHITECTURE.md`（目標の構成。自分の作業に関係する章）
4. `docs/GAME_QUALITY_STANDARDS.md`（ゲームを触るとき）
5. `docs/DEVELOPMENT_ROADMAP.md` の、自分の作業の行（**担当ファイル**と**完了の条件**）
6. 触るファイルは、全体を読んでから直す

## 1. 変えてはいけない前提
- 静的ホスティングだけ。ビルドの工程を作らない。npm のパッケージを足さない。
- 外から読み込んでよいのは、Three.js r128（`https://cdnjs.cloudflare.com/ajax/libs/three.js/r128/three.min.js`）、Firebase compat SDK 10.12.2（`https://cdn.jsdelivr.net/npm/firebase@10.12.2/`）、Google Fonts だけ。ほかを足すときはオーナーの了解を得る。
- Firebase は `neji-5913a` の Spark（無料）プラン。Cloud Functions は使わない。1日の読み書きは SYSTEM_ARCHITECTURE.md 7.2 の見積もりに収める。
- 広告なし、課金なし、外部への分析の送信なし（匿名のプレイ回数だけ）。
- 日本語と英語。スマホ優先。
- 特定の商用ゲームの名前・キャラクター・絵・ステージを使わない。

## 2. 守ること
1. **ゲームを消さない、簡単にしない。** 動いている機能（対戦、引き継ぎコード、デイリー、ショップ、まちめぐりなど）を、減らしたり弱めたりしない。直すために一時的に止める必要があるときは、指示した人に先に確かめる。
2. **担当ファイルだけを触る。** ロードマップの「担当ファイル」以外は変えない。ほかのファイルを直す必要があるときは、報告に「頼みたい変更」として書く。ほかの作業者が同じゲームを直している最中なら、そのファイルには手を出さない。
3. **データを壊さない。** localStorage のキーの名前と形、Firestore と RTDB のパスは変えない。形を変えるなら、古い形を読む移行のコードを書き（`KoboPlatform` の `MIGRATIONS`）、古いキーは消さない。移行は1回だけ動き、何度動いても結果が同じになるようにする。`fixtures/saves/` に古い形の例を足し、読み込めることをテストする。
4. **ルールを変えるときは、古いクライアントが動き続けるようにする。** ルールはオーナーがコンソールに貼り付ける。貼り付ける前でも後でも、新しいクライアントが動くこと（失敗したら、端末の保存だけで続ける）。報告には、貼り付けの手順と全文を入れる。
5. **偽物の機能を作らない。** 押しても何も起きないボタン、決め打ちの数字で作った「人気」や「ランキング」、「準備中」のまま置いておく欄は作らない。データがない欄は表示しない。
6. **画面に出る文字は `KoboI18n.t()` を通し、英語の訳を同じファイルに入れる。**
7. **全部の画面サイズで確かめる。** 320×568 から 414×896、横向き、ノッチあり、日本語と英語（TEST_PLAN.md 4章）。主なボタンが画面内にあり、44px以上あること。
8. **終わったと言う前にテストする。** `node tools/tests/run.js --vp quick` と、自分の作業のスイートを実行する。ルールや同期を変えたら `--live` も。テストがまだない部分は、自分で Playwright で確かめ、その方法を報告に書く。
9. **3D は重くしない。** 止まっているときは描画を休む。DPR の上限は2（重いゲームは1.5）。新しい処理を足したら fps を測る（perf スイート）。
10. **共通の層を使う。** 保存の補助、音、テーマ、乱数、日付（日本時間）、Firebase の初期化は `common/` のものを使い、ゲームの中に同じものをもう一度作らない。足りないものは報告に書く。
11. **対戦中はベストと保存を変えない**（versus.js の決まり）。デイリーとランキングに入れるのは、`mode` が `normal` か `daily` のときだけ。
12. **`sw.js` の `VERSION` を上げる**（P1-7 で自動になるまで）。ページを足したら `GAMES` に足す。
13. **コミットとプッシュは、指示されたときだけ。** `main` に入れると、両方の公開先に自動で反映されることを忘れない。`gh-pages` への push もする（自動化されるまで）。
14. **秘密の値を入れない。** GitHub Pages ではリポジトリ全体が公開されている。`firebase-config.js` の値は公開してよいもの。
15. **正直に報告する。** 確かめられなかったこと、残っている不具合、テストが落ちたままのものを、隠さずに書く。「たぶん動く」は「確かめていない」と書く。

## 3. 作業の進め方
1. 読む（0章）→ 担当ファイルと完了の条件を確かめる。
2. 今の動きを先に測る（テストを実行し、スクリーンショットを撮る）。直す前の状態を残す。
3. 小さく直し、そのたびに確かめる。
4. 監査の表（AUDIT.md 3章）で、自分が直したところの判定を更新したい場合は、報告に書く（AUDIT.md はロードマップの担当ではないので、作業者は直さない）。
5. 完了の報告を出す。

## 4. 完了の報告（この形で）
```
## 作業 <ID>：<名前>
- 変えたファイル：…（担当ファイルの外を触っていないこと）
- やったこと：…（3〜8行）
- データ：変えたキーや形と、移行のしかた（なければ「なし」）
- ルール：貼り付けが必要か（必要なら全文と手順）
- テスト：実行したスイートと結果（合格 n / 不合格 m）。落ちたものと理由
- 画面：確かめた画面サイズと言語。スクリーンショットのパス
- 残っている問題：…（ない場合も「確かめていないこと」を書く）
- 頼みたい変更：ほかの作業の担当ファイルへの変更の提案
```

## 5. よくある落とし穴
- `localStorage` は try/catch で包む（プライベートモードや容量の上限）。
- `cloud.js` は https でしか動かない。ローカルの http.server では同期のテストができないので、TEST_PLAN.md 5章の方法を使う。
- `KoboCloud.sync` の `'newest'` は、保存をまるごと上書きする。進行のデータには、フィールドごとのマージを登録する。
- `removeItem` は、P1-5 の前は同期されない（終わった回が復活する。AUDIT R3）。
- 日付は `KoboPlatform.jstDateKey()` を使う。`new Date().getDate()` は使わない。
- オーバーレイは画面の中に収め、中だけスクロールさせる。高さは `100dvh` と `--kobo-h`（i18n.js の `fitViewport`）に従う。
- AudioContext は、ユーザーが操作したときに作る（iOS）。
- WebGL の `webglcontextlost` を処理する（`KoboGame` の約束事）。
