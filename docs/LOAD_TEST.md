## まとめ

- **無料プランのままで、1日に遊ぶ人（DAU）はおよそ 750 人まで**です。いちばん先に尽きるのは Firestore の読み取り（1日5万件）で、その大半はランキングのボード（1つ見ると30件）です。
  - 書き込み（1日2万件）は約1,070人で尽きます。旧ランキング（kusogeRanks）への書き込みが 12/2 に止まると約1,230人になります。
  - Realtime Database（RTDB）は、データの転送（月10GB）で約1,000人、同時接続（100本）で約8,000人です（下の「前提」の遊び方のとき）。
- **Firebase Hosting（neji-5913a.web.app）は、はじめて来る人が1日 約460人まで**です（転送は1日360MB）。BUILD 40 では、はじめて来た人がオフライン用に全ゲームのファイル（gzip で約4.1MB）をまとめて落としていたので、約85人でした。BUILD 41 から、はじめに保存するのはハブとその部品だけ（gzip で約0.44MB。ハブのサムネイルも入れて）にして、ゲームは開いたときに保存します。ハブとゲーム2つを開く人で約0.78MB（hole を開く人だけは約2.1MB 増える）。2回目からはほとんど転送しません（更新のときも変わっていないファイルは 304）。GitHub Pages（seg1gpt0jpn.github.io）には1日の上限がありません。
- 200人が同時にランキングを読み書きし、50組が同時に対戦しても、**エラー0件、ルールでの拒否0件、待ち行列と部屋の残り0件**でした（直したあと）。
- 負荷テストで見つかった不具合を2つ、クライアントで直しました（匿名ログインの取り合い、RTDB の接続を閉じない）。**ルールは変えていません（Firebase コンソールに貼り直す必要はありません）。**

### Firestore：200人の流れ（1人 約70秒）

1. ハブを開く（`KoboCloud.sync`。Google でログインしている人は `nejiUsers` を読む）。「人気」の欄の `kbPlays` を2件読む。
2. 2つのゲームを4回遊ぶ（`KoboPlatform` に `play_start` → `best` → `play_end` を送る。ページが送るのと同じイベント）。
   rank.js が `kbBoards`（通算・週間・日間）、cloud.js が `kusogeRanks` と `nejiUsers`、achievements.js が `kbProfiles` に書く。
3. ランキングのページを開いて、2つのゲームの週間・日間・通算（6ボード）と総合（`kbProfiles`）を見る。もう一度同じボードを開いて、キャッシュから出ること（読み取り0件）を確かめる。
4. ページを閉じる（`visibilitychange` で残りを送る）。

200人のうち 40% は Google でログイン（エミュレーターのメールのアカウント）、50% はニックネームのあるゲスト（ランキングのときに匿名ログイン）、10% はニックネームなし。20秒かけて全員が始め、同時に200人でした。
`kbPlays` の +1 は、**今のクライアントにはまだ送る役がありません**（`platform.js` の `plays.pending()` を送るはずの rank.js にない）。ルールが想定している書き方（`FieldValue.increment(1)` を merge で、1ゲーム1日1回）で送り、表では「模擬」と分けています。

## 1人1日あたりの見積もり

無料枠（Spark）：Firestore は1日に読み取り 50,000・書き込み 20,000・削除 20,000、RTDB は同時接続 100・保存 1GB・転送 月10GB、Hosting は1日 360MB。

1日の遊び方を3つの型にして、上の「1回あたり」の値をかけました（型の混ぜ方は 60% / 30% / 10%。40% が Google でログイン）。

| 型 | 割合 | 1日の遊び方 | 読み取り | 書き込み | この型だけなら |
| --- | ---: | --- | ---: | ---: | ---: |
| 軽い | 60% | 1回開く・3回遊ぶ・ランキングは見ない | 3 | 11 | 1,890人 |
| ふつう | 30% | 2回開く・6回遊ぶ・ボードを2つ見る・オンライン6分 | 66 | 21 | 750人 |
| よく遊ぶ | 10% | 4回開く・20回遊ぶ・ボード12＋総合2・オンライン30分 | 430 | 59 | 116人 |
| **混ぜた平均** | | | **65** | **19** | **約 770人（読み取りで決まる）** |

- 書き込みの内訳（ふつうの型）：kbBoards 12.4、nejiUsers 4.0、kusogeRanks 2.8、kbProfiles 2.0。kbBoards は1台で1日40件まで（rank.js の `DAY_WRITES`）、kbProfiles は4件まで。
- 削除はふだん0件です（アカウントの削除のときだけ。1人数件）。
- kbPlays の送信を足すと、1人1日 1〜3件増えます（混ぜた平均で約1.5件）。
- RTDB：オンラインで遊ぶ時間を1人1日平均4.8分、いちばん混む1時間に1日の15%が集まるとすると、同時接続100本で **約8,300人**（直す前は、試合のあともページを閉じるまで接続が残るので約3,100人）。転送は1人あたり月 約9.4MB で、月10GBなら **約1,060人**。保存は試合のあと部屋を消すので、ほぼ0です。
- Hosting（`pwa-offline.js` で、はじめての訪問で実際にサーバーが送ったファイルを数え、gzip にした大きさ）：
  - BUILD 40（全部を最初に保存）：4.12MB（うち hole の街のデータが 1.97MB、画像が約0.6MB）→ 360MB ÷ 4.12MB で **1日 約85人**。
  - BUILD 41（ハブだけ最初に保存）：ハブだけなら **0.44MB → 約820人**。ゲームは開いたときに、そのページと ENGINES（ふつうのゲームで gzip 25〜80KB、hole だけは14都市で約2.1MB）。ハブ＋ゲーム2つ（平均）で約0.78MB → **1日 約460人**。
  - three.js は cdnjs、SDK は jsdelivr から来るので Hosting には入りません。インストール用の大きなアイコン（512px）は、ブラウザがインストールするときに自分で取るので、最初の保存から外しました。

## 見つかったところと、直したもの

### 直したもの（クライアントのコードだけ）

1. **匿名ログインの取り合い**（`common/cloud.js` の `ensureGuest`）。rank.js・achievements.js・versus.js が同時に `ensureGuest()` を呼ぶと、`signInAnonymously()` が2回走って匿名のアカウントが2つできていました。先に書き始めたランキングの書き込み（パスは1つ目の uid、トークンは2つ目）がルールで拒否され、そのプレイの週間・日間の記録が載らないことがありました（直す前の20人のテストで、kbBoards の書き込み164件のうち20件が拒否。どれもゲストの最初のプレイ）。いまは1回にまとめます。単体テスト `cloud.test.js` に足しました。
2. **RTDB の接続を閉じていなかった**（`common/versus.js`・`hole/index.html`・`shogi/index.html`）。前は、一度オンライン対戦を開くと、ページを閉じるまで接続（無料プランは同時に100本まで）が残っていました。いまは、待ち行列にも部屋にもいない状態が20秒続いたら `goOffline()` し、次にオンラインを開くときに `goOnline()` します。閉じると、サーバーに残した `onDisconnect` の片付けも走ります。
3. **旧ランキングへの書き込みを、ルールが閉じたあとは送らない**（`common/cloud.js`）。2026-12-02 0:00（日本時間）から `kusogeRanks` は読むだけになります（ルールの `legacyOpen()`）。前は、そのあとも記録が変わるたびに拒否される書き込みを送り続けるところでした。単体テストを足しました。

### まだのもの（提案）

1. **ランキングのボードは1つで30件読む**（読み取りの9割）。よく遊ぶ人がボードを次々に切り替えると、1日数百件になります。案：最初は上位10件だけ読み、「もっと見る」で残りを読む（`startAfter`）。ただし rank.js の「30位に届かなければ週間・日間に書かない」（書き込みを減らす仕組み）は30件のキャッシュを使っているので、いっしょに考える必要があります。通算のボードはキャッシュを5分より長くしてもよい。
2. **旧総合（kusogeRanks を全部、最大1,000件）**。1日キャッシュですが、旧ランキングに載っている人の数だけ、見る人1人ごとに読みます。旧ランキングのタブは 12/2 で消えるので、そのままにしました。`KoboCloud.loadRanks()`（同じく1,000件）はどこからも呼ばれていません。
3. **kbPlays（人気）の送信はまだない**。作るときは、全員が同じ文書（`kbPlays/w<週>`）に書くので、本番では1つの文書に1秒1回くらいまでが目安です（エミュレーターではこの上限は再現されません）。DAU が数百人なら問題ありませんが、増えたら文書を分ける（例 `w<週>~<0〜9>` に分けて、ハブで10件読んで足す）ことを考えます。分けるならルールも変わります。
4. **Hosting の初回の転送**（BUILD 41 で直しました）。最初に保存するのはハブと `common/` だけになり、ゲームは開いたときにそのゲームの ENGINES（hole は全部の街）をまとめて保存します。オフラインで、開いたことのないゲームを開くと `offline.html` が出ます。残る大きなものは hole の街のデータ（hole を開いた人だけ、約2.1MB）です。さらに減らすなら、hole で選んだ街だけを保存する（そのかわり、オフラインでは開いたことのある街だけになります）。
5. **hole の転送が多い**（3つのゲームの中でいちばん多い）。位置を0.2秒ごと × 4人分（CPU の穴も）送り、全員が全員の位置を受け取るためです。オンラインの hole が流行ったら、RTDB の月10GBが先に来ます。

## ルール

ルール（`firestore.rules`・`database.rules.json`）は変えていません。**Firebase コンソールに貼り直す必要はありません。** `node tools/tests/rules/run.js` は全部通ります。

## 前提と限界

- 時間はすべてエミュレーター（同じマシン、ネットなし）の値です。本番の速さではなく、「同時に200人・100人が動いてもクライアントの手順が詰まらず、エラーや拒否が出ない」ことの確認です。
- エミュレーターは、無料枠の上限（同時接続100本、1つの文書に1秒1回の書き込み）を再現しません。上限は数えて見積もりました。
- Firestore の読み取りは、SDK の代わり（`shim.js`）が1回の呼び出しを1回の REST として数えています（get は1件、クエリは返した件数で最低1件）。本物の SDK もオフラインの永続化を使っていないので同じ数になります。ルールで拒否された読み取りは、今回は0件でした。
- RTDB の「人」は、ゲームの画面なしで、ページと同じパス・同じ間隔で書きます（書く種類が本物のページと同じであることは `rules/clients.js` の一覧で確かめています）。試合の長さは短くしてあるので、転送は「1人1分あたり」に直して見積もりました。
- 1日の遊び方の型（上の表）は仮定です。実際の数字（ハブの「人気」の回数など）が集まったら、`run.js` の `SCENARIOS` を直して `node tools/tests/load/run.js --estimate` で計算し直せます。
